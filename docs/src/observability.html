두 출구
Amplitude 와 Firebase 가 병행한다. 같은 이벤트가 두 곳에 쌓이므로 집계할 때 출처를 섞지 않는다.

1어디로 흘러가는가

ViewModel 이 Observability.log(channel) { payload } 를 부르면 파이프라인이 채널별로 출구를 고른다.

채널무엇Firebase AnalyticsAmplitudeCrashlytics
BUSINESS사용자 행동○○–
PERFORMANCETTI · 잼 · 메모리○○–
DIAGNOSTIC에러 · 경고––○ (WARN 이상)
모든 이벤트에 screen 이 붙는다 이벤트가 난 시점의 화면 경로다. 성능·진단 페이로드에는 화면 필드가 따로 없어서 이 값이 유일한 출처다. Amplitude 키가 비면 Amplitude 출구를 아예 달지 않는다. Firebase 로는 계속 나간다.

6무엇을 볼 수 있나

지금 이벤트만으로 만들 수 있는 것들. 괄호는 걸어야 할 속성 필터다.

보고 싶은 것만드는 법
온보딩 완주율퍼널: login_screen_view (fresh) → login_attempt → login_result (success) → signup_complete
단계별 이탈퍼널에 onboarding_step_complete 를 step 필터로 6번 넣는다
가입 소요 시간signup_complete 의 duration_ms 중앙값
닉네임 병목nickname_check 를 available 로 나눈다
탐색 → 참여 전환퍼널: explore_home_view → challenge_card_click → challenge_detail_view → challenge_join_result (success)
인기 섹션 vs 목록challenge_card_click 을 source 로 나눈다
게이트별 이탈challenge_join_result (success = false) 를 error_code 로 나눈다
빈 결과율explore_empty_result ÷ explore_list_view
카테고리 편중category_grid_click 을 category 로 나눈다
방 재방문room_view 의 주간 고유 사용자
단일 기기 정책 부작용session_expired 를 trigger 로 나눈다
화면별 체감 속도perf_tti 의 total_millis 를 screen_name 으로 나눈다

Amplitude 에 RuleUp 제품 지표 대시보드를 만들어 뒀다. 위 항목 중 8개가 차트로 들어가 있다. 다만 개인 스페이스에 있어 지금은 만든 사람만 볼 수 있다.

7알려진 함정

Amplitude 에 사용자 식별자가 없다 UserIdentitySync 가 Firebase Analytics 와 Crashlytics 에만 setUserId 를 부른다. 그래서 Amplitude 의 "사용자"는 앱 설치 단위이고, 재설치·기기 교체는 새 사람으로 잡힌다. 온보딩 퍼널은 어차피 설치 단위라 영향이 작지만, 리텐션·티어처럼 계정을 따라가야 하는 지표는 지금 Amplitude 로 낼 수 없다.
Firebase 는 조용히 자르고 Amplitude 는 안 자른다 Firebase 는 이름 40자 · 키 40자 · 값 100자 · 이벤트당 파라미터 25개에서 자른다. 잘린 값은 분석에서 다른 값과 뭉치므로 매퍼가 절단 횟수를 따로 센다. 두 도구의 같은 이벤트 값이 다르면 Firebase 쪽이 잘린 것이다. Firebase 는 Boolean 을 0/1 로 바꾸고 Amplitude 는 true/false 그대로 둔다.
중복 전송이 의도인 곳이 둘 explore_filter_apply 와 explore_empty_result 는 같은 조작에서 함께 나간다 — 분모가 달라 합치면 빈 결과율을 못 낸다. challenge_join_result 는 서버도 남기지만 클라도 남긴다 — challenge_id 를 잇는 건 클라에서만 되고, 퍼널 근거가 갈라지는 것보다 중복이 낫다.
CI 빌드에는 Amplitude 키가 없다 워크플로가 local.properties 를 만들지 않아 CI 가 뽑은 APK 는 Amplitude 출구 없이 나간다. 로컬 빌드만 키를 갖는다.

8아직 없는 것

카탈로그가 없는 feature 다섯. verification(인증) · notification(알림) · profile(마이) · report(신고) · support(문의) 에는 이벤트 팩토리가 없다. 그 도메인의 퍼널은 만들 수 없다. 특히 인증은 제품의 중심인데 "인증 제출 → 판정 결과"를 볼 방법이 지금 없다.

새 이벤트를 추가하려면

#할 일
1그 도메인의 observability/<Feature>Events.kt 에 팩토리 함수를 만든다. 이름은 snake_case
2골든 테스트를 같이 쓴다. 이름을 바꿀 때 대시보드가 조용히 비는 대신 테스트가 깨진다
3ViewModel 에서 observability.log(Channel.BUSINESS) { … } 로 부른다
4OBSERVABILITY.md 표에 한 줄 더한다. 코드와 같은 PR 에 있어야 안 썩는다

속성을 정할 때 둘. 모르는 값에 빈 문자열을 넣지 않는다 — 키를 빼면 결측으로 잡히고, 빈 문자열은 가짜 분류를 하나 만든다. 분모와 분자를 같은 축으로 만든다 — challenge_id 처럼 단계를 잇는 키가 없으면 전환율을 계산할 수 없다.

이름과 속성의 진실은 코드다. 이 문서가 코드와 어긋나면 코드가 맞다. 원본은 레포의 OBSERVABILITY.md — 이벤트를 늘리거나 이름을 바꾸는 PR 이 함께 고친다.
